# Extension integration tests and local live checks

These are regression tests: they preserve working user flows as the extension changes. Playwright loads the built extension, including its actual service worker, offscreen document, Core WebAssembly, model, encrypted vault, device keys, and native side panel. Extension APIs and detection results are not stubbed.

The default 38-test PR suite uses controlled HTML served through Playwright routing at `https://chatgpt.com`. It requires no ChatGPT account, network access to ChatGPT, or repository secrets. This makes PR checks repeatable, but it does not establish compatibility with today's live ChatGPT markup or authentication flow. Its editor fixtures verify extension integration and do not simulate authenticated sessions.

A separate live suite runs locally against the real ChatGPT site with an authenticated test-account session. Its tests use the actual editor and server responses, without replacing ChatGPT pages or responses. A local pre-commit hook runs this suite and prints and saves an execution receipt. The two suites have separate configurations and commands: `npm run test:e2e` continues to run the existing 38 extension integration tests, while authenticated live tests stay outside CI.

## Run locally

```sh
npm ci
npx playwright install chrome
npm run test:integration
```

On a Linux machine that needs browser system libraries, use `npx playwright install --with-deps chrome`. The E2E command builds `dist/` before loading it. The old `npm run test:e2e` command remains an alias. To select a test, pass Playwright arguments, for example:

```sh
npm run test:integration -- --grep "Remember this device"
```

Reports, traces and screenshots are generated by Playwright and uploaded by CI for diagnosing failures. The long-prompt test attaches observed insertion, keyboard-interaction and scan timings. These measurements are evidence, not a performance SLA; an acceptable typing-latency budget has not been specified.

The default suite launches Google Chrome with `channel: "chrome"`, using a fresh temporary profile for every test. It installs the extension through Chrome's [DevTools `Extensions.loadUnpacked` API](https://chromedevtools.github.io/devtools-protocol/tot/Extensions/#method-loadUnpacked), rather than the command-line sideload flag removed from branded Chrome. Native side panels are attached through a second DevTools connection. Only Google Chrome is tested; no Firefox, Edge, Brave or bundled Chromium jobs are configured. The CI report records the Chrome version used.

## CI triggers

Run the suite for pull requests targeting `main`, including updates to an open PR, and for pushes to `main`, including merges. The PR run catches regressions before merge; the push run verifies the integrated result. Manual dispatch supports reruns on demand. Run the OS matrix on Linux, macOS and Windows so the requested Mac and Windows coverage is included. Use the extension-integration status checks as required checks in branch protection if merges should be blocked by failures; committing a workflow alone does not configure branch protection.

If the repository starts using GitHub's merge queue, add the `merge_group` trigger so required checks also run for queued merges. See [GitHub's workflow event reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows).

## Local live suite and pre-commit hook

Install the repository-local hook once per clone:

```sh
npm run hooks:install
```

The hook runs the complete configured live suite before each commit. A failed test, missing authentication, inaccessible editor or pending browser verification blocks the commit. Live tests run locally; the existing account-free 38-test suite remains in CI.

Use a dedicated ChatGPT test account. To open its separate Chrome profile and keep that browser available for the tests, run:

```sh
npm run test:live:auth -- --keep-open
```

Sign in directly in that window and complete any human verification yourself. Press Enter in the helper's terminal once the editor is ready, then leave Chrome and the helper process open. The helper verifies the session, saves private authentication state in `.playwright/chatgpt-auth.json`, and records the local browser connection in `.playwright/live-browser.json`. The profile, connection metadata and session files are ignored by Git. Login does not record screenshots or traces, and no password is entered into a test script.

Run the same local check manually with:

```sh
npm run test:e2e:live
```

The runner connects to the already-running browser using the saved connection metadata, an explicit `CHATGPT_CDP_ENDPOINT`, or the open helper profile. It does not automatically start or restart Chrome. It creates test tabs and a temporary extension build, then cleans up only test-owned resources, leaving the original browser and its tabs open. The explicit-endpoint mode refuses to replace an existing DataFog installation and vault; helper-profile mode may replace the helper's known test build.

For another already-running test Chrome with remote debugging enabled, set its existing localhost HTTP endpoint in the terminal used for tests and commits. Replace `PORT` with that browser's debugging port:

```sh
export CHATGPT_CDP_ENDPOINT="http://127.0.0.1:PORT"
npm run test:e2e:live
```

In PowerShell:

```powershell
$env:CHATGPT_CDP_ENDPOINT = "http://127.0.0.1:PORT"
npm run test:e2e:live
```

`CHATGPT_USE_OPEN_PROFILE=1` explicitly selects the helper's open profile. A valid login alone does not establish that ChatGPT accepts the browser: the site can return HTTP 403 before showing the editor. The suite reports that access failure separately from expired authentication. Complete any browser verification manually and leave the accepted window open before trying the local check again. The runner does not complete or bypass verification prompts.

### Printed and saved receipt

Every completed test run prints its result and saves private receipts:

- `.playwright/live-receipt.json` contains structured execution evidence.
- `.playwright/live-receipt.txt` contains the readable result.

The receipt records the host, platform, run time, Chrome version, per-test statuses, working-tree code fingerprint and staged Git tree hash. A full-suite `PASS` requires every configured test to pass, with no skipped or flaky results. Filtered manual runs are identified as selected runs and do not establish a full-suite pass. The hook invokes the complete suite for the commit check.

Tests execute the working tree without automatically stashing changes. The staged tree hash is recorded separately: when files are partially staged, the tested working files can differ from the contents that will be committed. Inspect that difference when using the receipt as evidence for a commit. Authentication state and browser profiles stay private and are not uploaded to CI.

### Live coverage

The 15 core live cases are implemented in `e2e/live/chatgpt.spec.ts`; the receipt supplies the actual result for a particular run:

| Live flow                                                                  | Cases |
| -------------------------------------------------------------------------- | ----- |
| README sample detection and each of the five opt-in detectors              | 6     |
| Redact/Undo/Redo with editor changes, Dismiss, allowlist and checking off  | 3     |
| Pseudonymize review/replace/Undo and Not sensitive until locking           | 2     |
| Send-button and Enter blocking, followed by Send anyway                    | 2     |
| A real assistant response containing a marker, then Restore, Copy and Hide | 1     |
| Detection and Redact in a temporary chat                                   | 1     |

The send and restoration cases submit synthetic test prompts to real temporary chats. Other live cases edit test text without intentionally submitting it. The restoration case waits for the real answer's Copy control before restoring; it does not assert restoration while an answer is still streaming. Canvas, editing earlier messages, native IME input and attachment integration have not yet been added to the live suite. The broader default suite continues to cover their controlled browser-event or layout scenarios where documented below.

Three additional live cases are registered only when their actual test-account URLs are provided:

| Surface       | Local environment variable  |
| ------------- | --------------------------- |
| Existing chat | `CHATGPT_EXISTING_CHAT_URL` |
| Project       | `CHATGPT_PROJECT_URL`       |
| Custom GPT    | `CHATGPT_CUSTOM_GPT_URL`    |

Each configured URL must be on `https://chatgpt.com`. Its case checks detection and Redact in the actual surface's composer and clears the unsent text afterward. Absent URLs do not register those cases; placeholder paths never stand in for a real account surface. Set these variables in the terminal used for tests and commits to include those cases in the full local run. The coverage matrix below describes the default PR suite; live results are recorded in the local receipts.

## Known surface and restoration limits

The extension scans the first visible editor matching `#prompt-textarea`, `form [contenteditable='true']`, or `form textarea`. An editor inside an iframe or a shadow root, a canvas-only editor, or a page with several independently editable messages may not be covered. The automated missing-composer case verifies the toolbar `!` warning; it does not imply that every unsupported live layout has been observed. Passing the default PR suite does not establish live-surface coverage; only surfaces actually visited and checked by an authenticated live run should be marked verified.

Restoration covers the latest answer that the current selectors can find. It shows originals in closed shadow roots; ChatGPT's scripts and text do not receive them. Copy restored answer uses the extension's restored snapshot. New streaming chunks and a ChatGPT redraw do not automatically update that snapshot; choose Restore latest answer again. Hide originals and locking the vault remove the displayed originals.

## Release smoke test in Google Chrome

On both Mac and Windows, load the release build in Google Chrome and perform the manual checks in the matrix. Record the Chrome version, extension commit/version, OS, logged-in state and any unsupported live surface. Use synthetic values and a test vault. Keep any real credentials or user prompt text out of CI traces and screenshots.
